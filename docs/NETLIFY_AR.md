# ربط Netlify

إعداد البناء مُجهّز في `netlify.toml` بجذر المستودع. هذا الإعداد لا يعني أن التطبيق جاهز للتشغيل السحابي؛ طبقة البيانات الحالية محلية.

## إعداد المشروع المستهدف

| الإعداد | القيمة |
|---|---|
| مشروع Netlify | `nwc-violations-app` |
| مستودع GitHub المطلوب | `abuahad2000/nwc-violations-app` |
| فرع الإنتاج | `master` |
| مجلد البناء الأساسي | `apps/web` |
| أمر البناء | `npm run build` |
| مجلد النشر، نسبةً إلى المجلد الأساسي | `.next` |
| Node.js | `24` |

تم تحديد محوّل Next.js صراحةً في ملف الإعداد لأن المشروع الموجود كان يُنشر كموقع ثابت دون محوّل. لا تستخدم رفع مجلد HTML يدويًا أو أمر `start:local`، فهو يشغّل PostgreSQL داخل WSL محليًا.

## المتطلبات المتبقية قبل نشر نسخة تشغيلية

1. التحقق من اتصال مشروع Netlify بالمستودع والفرع أعلاه بعد تسجيل الدخول.
2. نقل تخزين الحسابات والجلسات والبلاغات والإجراءات من SQLite المحلي إلى تخزين سحابي دائم، وتعديل استعلامات التطبيق ومعاملاته واختبارها. تغيير متغير الاتصال وحده لا ينقل SQLite إلى PostgreSQL.
3. توفير اتصال PostgreSQL يدعم PostGIS عبر `POSTGIS_URL` في بيئة الخادم، بدل عنوان `127.0.0.1` المحلي، والتحقق من التصنيف المكاني.
4. نقل البيانات التشغيلية إلى التخزين الخاص وإنشاء حساب الدخول؛ بيانات الجهاز والحساب المحلي لا تُرفع مع مستودع الكود.
5. اختبار تسجيل الدخول والصلاحيات والشارتات والخريطة وحفظ الإجراءات واستمرار البيانات بعد إعادة النشر، ثم تفعيل نسخة الإنتاج.

وظائف Netlify تعمل في بيئة مؤقتة؛ لا يصلح ملف SQLite المحلي فيها لحفظ بيانات هذا التطبيق بشكل دائم. لا تستخدم `/tmp` كبديل لتخزين الحسابات والإجراءات.

لا توجد مفاتيح أو كلمات مرور في ملف إعداد البناء. يجب إدخال أسرار الاتصال في إعدادات متغيرات البيئة داخل Netlify بصلاحية الخادم، دون بادئة `NEXT_PUBLIC_`.
